Tổng quan & kịch bản

Công ty muốn chuyển DB on-prem sang AWS với downtime tối thiểu. Với cùng engine (homogeneous, ví dụ MySQL → Aurora MySQL) bạn dùng DMS full load + CDC. Với khác engine (heterogeneous, ví dụ Oracle → Aurora PostgreSQL) phải chuyển schema/code bằng SCT (hoặc DMS Schema Conversion) trước, DMS lo phần dữ liệu.

Source DB→ đọc →DMS replication instance→ ghi →Target DB
Full load→ cache thay đổi →CDC apply→ lag ~0 →Cutover
Chế độPaper lab mặc định (mục 1, 6 và các câu "Dự đoán"). Mục 2-5, 7 có nhánh Sandbox tùy chọn: RDS MySQL nguồn + đích, DMS dms.t3.micro. Chi phí khoảng vài chục cent nếu dọn kịp trong 1-2 giờ.
Yêu cầu sandboxAWS CLI v2, default VPC (RDS và DMS dùng chung default security group, đã cho phép traffic nội bộ), một máy trong VPC có mysql client (EC2 nhỏ hoặc CloudShell VPC environment) để tạo bảng/dữ liệu.
Regionap-southeast-1 (hoặc region bạn quen)
Liên hệ đề thi — sửa các bẫy:
  • CDC với MySQL nguồn cần binlog bật, binlog_format=ROW; trên RDS cần automated backup retention > 0.
  • Full load + CDC để cutover gần như không downtime; full load thuần thì cần ngừng ghi.
  • DMS không tự chuyển schema khác engine: cần SCT. DMS chỉ tạo bảng + primary key, không tạo secondary index, FK, trigger... (dựng bằng native tool/SCT).
  • DB hàng chục TB, băng thông yếu: SCT extraction agents/Snowball Edge rồi DMS CDC bắt kịp. Server/VM dùng MGN, file dùng DataSync.
  • Cùng engine, DB lớn, chấp nhận downtime: native tools (mysqldump, pg_dump, Oracle Data Pump, backup/restore) thường đơn giản, nhanh hơn.
Mẹo: bấm vào ô có viền nét đứt để copy. Tick checkbox bên phải mỗi bước để theo dõi tiến độ.

1Chọn công cụ và thiết kế (paper)

Trả lời các câu hỏi thiết kế trước khi đụng vào console. Đây là phần quan trọng nhất cho đề thi.

Thành phầnVai trò
Replication instanceEC2 do DMS quản lý chạy task; chọn class theo tải (dms.t3 cho lab, dms.c5/r5 cho production); cần storage cho log và cache CDC. Nên Multi-AZ khi chạy lâu cho production.
Source/target endpointThông tin kết nối (engine, host, port, user, SSL). Phải Test connection thành công từ replication instance.
Replication taskĐịnh nghĩa migration type + table mappings + task settings.
Table mappingsJSON: selection rules (include/exclude) và transformation rules (rename schema/table/column...).
ValidationSo sánh dữ liệu nguồn và đích trong lúc/ sau khi migrate (EnableValidation).
Migration typeKhi dùng

full-load-and-cdcCopy + đồng bộ thay đổi liên tục; cutover ngắn (migrate gần như không downtime)
cdcChỉ thay đổi từ một điểm (log position/thời gian), thường sau khi đã load bằng native backup hoặc Snowball
  1. 🔮 Dự đoán: MySQL 8 on-prem 800 GB, yêu cầu downtime dưới 5 phút, cùng engine sang Aurora MySQL. Bạn chọn migration type nào và cần chuẩn bị gì ở nguồn?
    Xem kết quảfull-load-and-cdc. Nguồn: bật binary log, binlog_format=ROW, binlog_row_image=FULL, tăng binlog retention (RDS: CALL mysql.rds_set_configuration('binlog retention hours', 24)), user DMS có quyền SELECT + REPLICATION CLIENT + REPLICATION SLAVE. Tạo schema (bảng, index, FK) ở đích trước bằng mysqldump --no-data.
  2. 🔮 Dự đoán: cùng bài toán nhưng DB 80 TB, đường truyền 100 Mbps, và chấp nhận downtime cuối tuần. DMS full load qua mạng có hợp lý không?
    Xem kết quảKhông. 80 TB qua 100 Mbps mất vài tháng (ước lượng thô: 80 TB / ~10 MB/s thực tế). Hướng: copy backup/snapshot offline (Snowball Edge nếu còn dùng được, hoặc Direct Connect nâng băng thông), restore native, rồi dùng DMS chế độ cdc để bắt kịp thay đổi. Lưu ý: Snowball Edge từ 11/2025 chỉ còn cho khách hàng hiện hữu; nhưng đề thi vẫn có thể nhắc, và AWS gợi ý DataSync/Data Transfer Terminal cho khách mới.
  3. 🔮 Dự đoán: cùng engine, DB 2 TB, cutover cuối tuần 8 giờ downtime được. DMS hay native tool?
    Xem kết quảNative (mysqldump/xtrabackup/snapshot restore hoặc Aurora read replica từ RDS MySQL) thường đơn giản và nhanh hơn. DMS tỏa sáng khi cần giảm downtime (CDC), cần lọc/biến đổi bảng, hoặc khác engine. Còn có DMS Homogeneous Data Migrations: dùng native tool ở phía sau, serverless, cho MySQL/PostgreSQL/MariaDB/MongoDB cùng engine.

2Sandbox (tùy chọn): RDS MySQL nguồn + đích, binlog

Tạo hai RDS MySQL nhỏ. Nguồn có binlog ROW. Bỏ qua mục này nếu chỉ làm paper lab.

  1. Khai báo biến và tạo parameter group cho nguồn với binlog_format=ROW.
    export AWS_REGION=ap-southeast-1 PW="Lab_Only_Change_123" aws rds create-db-parameter-group --db-parameter-group-name sap-dms-src-mysql8 --db-parameter-group-family mysql8.0 --description "binlog ROW for DMS" aws rds modify-db-parameter-group --db-parameter-group-name sap-dms-src-mysql8 --parameters "ParameterName=binlog_format,ParameterValue=ROW,ApplyMethod=immediate"
    Mật khẩu trên chỉ là ví dụ cho lab dùng một lần. Không dùng lại ở nơi khác và không commit vào git.
  2. 🔮 Dự đoán: nếu tạo nguồn với --backup-retention-period 0, CDC có chạy được không? Hãy tạo nguồn với retention 1 (bật binlog) và đích:
    aws rds create-db-instance --db-instance-identifier dms-src --engine mysql --db-instance-class db.t3.micro --allocated-storage 20 --master-username admin --master-user-password "$PW" --backup-retention-period 1 --db-parameter-group-name sap-dms-src-mysql8 --no-multi-az aws rds create-db-instance --db-instance-identifier dms-tgt --engine mysql --db-instance-class db.t3.micro --allocated-storage 20 --master-username admin --master-user-password "$PW" --backup-retention-period 0 --no-multi-az aws rds wait db-instance-available --db-instance-identifier dms-src; aws rds wait db-instance-available --db-instance-identifier dms-tgt aws rds describe-db-instances --query "DBInstances[].[DBInstanceIdentifier,Endpoint.Address]" --output text
    Xem kết quảMất khoảng 5-10 phút. Với retention 0, RDS không bật binary log nên CDC không thể chạy (xem Phá thử). In ra 2 endpoint dạng dms-src.xxxx.ap-southeast-1.rds.amazonaws.com (ví dụ); ghi lại để dùng ở mục 3 (SRC_HOST, TGT_HOST).
  3. Từ máy trong VPC có mysql client, tạo dữ liệu mẫu ở nguồn và cùng schema (không dữ liệu) ở đích, đặt binlog retention.
    SCHEMA="CREATE DATABASE shop; CREATE TABLE shop.orders (id INT PRIMARY KEY AUTO_INCREMENT, item VARCHAR(50), qty INT);" mysql -h SRC_HOST -u admin -p"$PW" -e "$SCHEMA INSERT INTO shop.orders(item,qty) VALUES (\"a\",1),(\"b\",2),(\"c\",3); CALL mysql.rds_set_configuration(\"binlog retention hours\", 24);" mysql -h TGT_HOST -u admin -p"$PW" -e "$SCHEMA"
    Dùng master user admin làm DMS user cho nhanh trong lab. Production nên tạo user riêng chỉ có SELECT + REPLICATION CLIENT + REPLICATION SLAVE. Xác nhận ROW: SHOW VARIABLES LIKE 'binlog_format'; (kết nối mới).

3Replication instance & endpoints

Tạo replication instance, hai endpoint, và Test connection. Console sẽ tạo service role tự động, còn dùng CLI thì cần role dms-vpc-role có sẵn.

  1. (CLI, tài khoản chưa dùng DMS) tạo role bắt buộc, đúng tên dms-vpc-role.
    aws iam get-role --role-name dms-vpc-role >/dev/null 2>&1 || { aws iam create-role --role-name dms-vpc-role --assume-role-policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Principal\":{\"Service\":\"dms.amazonaws.com\"},\"Action\":\"sts:AssumeRole\"}]}" && aws iam attach-role-policy --role-name dms-vpc-role --policy-arn arn:aws:iam::aws:policy/service-role/AmazonDMSVPCManagementRole; }
    Console: bỏ qua bước này.
  2. 🔮 Dự đoán: khi nào replication instance chuyển sang available? Tạo:
    aws dms create-replication-instance --replication-instance-identifier sap-dms-ri --replication-instance-class dms.t3.micro --allocated-storage 20 --no-publicly-accessible --no-multi-az aws dms wait replication-instance-available --filters Name=replication-instance-id,Values=sap-dms-ri export RI_ARN=$(aws dms describe-replication-instances --filters Name=replication-instance-id,Values=sap-dms-ri --query "ReplicationInstances[0].ReplicationInstanceArn" --output text); echo $RI_ARN
    Xem kết quảThường 5-15 phút. Console: DMS → Replication instances → Create (chọn VPC chứa RDS, bỏ Public access). In ra ARN dạng arn:aws:dms:ap-southeast-1:123456789012:rep:XXXX (ví dụ). Không có --no-publicly-accessible mặc định là public.
  3. Tạo hai endpoint (thay SRC_HOST/TGT_HOST).
    export SRC_EP=$(aws dms create-endpoint --endpoint-identifier sap-src --endpoint-type source --engine-name mysql --server-name SRC_HOST --port 3306 --username admin --password "$PW" --query Endpoint.EndpointArn --output text) export TGT_EP=$(aws dms create-endpoint --endpoint-identifier sap-tgt --endpoint-type target --engine-name mysql --server-name TGT_HOST --port 3306 --username admin --password "$PW" --query Endpoint.EndpointArn --output text) echo $SRC_EP $TGT_EP
  4. 🔮 Dự đoán: status của test-connection?
    for E in $SRC_EP $TGT_EP; do aws dms test-connection --replication-instance-arn $RI_ARN --endpoint-arn $E >/dev/null; done; sleep 60; aws dms describe-connections --query "Connections[].[EndpointIdentifier,Status,LastFailureMessage]" --output text
    Xem kết quảMỗi endpoint successful (ví dụ sap-src successful None). Nếu failed: kiểm tra security group (3306 từ replication instance), sai mật khẩu, DB chưa available; xem LastFailureMessage. Có thể chờ lâu hơn 60 giây, chạy lại describe-connections.

4Task, table mappings, validation

Tạo task full-load-and-cdc, chọn bảng bằng selection rule và bật validation.

  1. Tạo table mappings và task settings (JSON hợp lệ). Mapping include mọi bảng của schema shop, loại bảng tmp_%.
    cat > tm.json <<EOF {"rules":[ {"rule-type":"selection","rule-id":"1","rule-name":"inc-shop","object-locator":{"schema-name":"shop","table-name":"%"},"rule-action":"include"}, {"rule-type":"selection","rule-id":"2","rule-name":"exc-tmp","object-locator":{"schema-name":"shop","table-name":"tmp_%"},"rule-action":"exclude"}]} EOF cat > ts.json <<EOF {"TargetMetadata":{"SupportLobs":true,"LimitedSizeLobMode":true,"LobMaxSize":32}, "FullLoadSettings":{"TargetTablePrepMode":"DO_NOTHING"}, "ValidationSettings":{"EnableValidation":true}} EOF python3 -c "import json;[json.load(open(f)) for f in ('tm.json','ts.json')];print('JSON ok')"
    DO_NOTHING vì bạn đã tạo schema ở đích (có index/FK). Với DROP_AND_CREATE DMS tạo lại bảng nhưng chỉ có cột + primary key. Transformation rule (đổi tên schema/bảng/cột, thêm cột...) dùng "rule-type":"transformation" cùng "rule-action":"rename".
  2. 🔮 Dự đoán: sau khi start, task ở trạng thái nào lâu dài, stopped hay running? Tạo và chạy:
    export TASK_ARN=$(aws dms create-replication-task --replication-task-identifier sap-dms-task --source-endpoint-arn $SRC_EP --target-endpoint-arn $TGT_EP --replication-instance-arn $RI_ARN --migration-type full-load-and-cdc --table-mappings file://tm.json --replication-task-settings file://ts.json --query ReplicationTask.ReplicationTaskArn --output text) aws dms wait replication-task-ready --filters Name=replication-task-arn,Values=$TASK_ARN aws dms start-replication-task --replication-task-arn $TASK_ARN --start-replication-task-type start-replication sleep 90; aws dms describe-replication-tasks --filters Name=replication-task-arn,Values=$TASK_ARN --query "ReplicationTasks[0].[Status,ReplicationTaskStats.FullLoadProgressPercent]" --output text
    Xem kết quảVí dụ: running 100. Full load xong (100%) nhưng task vẫn running để áp dụng CDC liên tục; một task full-load thuần mới tự chuyển stopped khi xong. Nếu status failed, xem mục Phá thử/CloudWatch Logs.
  3. Xem thống kê bảng và validation.
    aws dms describe-table-statistics --replication-task-arn $TASK_ARN --query "TableStatistics[].[SchemaName,TableName,FullLoadRows,Inserts,ValidationState]" --output text
    Xem kết quảVí dụ: shop orders 3 0 Validated. Trạng thái Pending records hoặc Mismatched records là dấu hiệu cần điều tra trước cutover.

5CDC và cutover

Thấy thay đổi ở nguồn tự chảy sang đích, rồi luyện quy trình cutover.

  1. 🔮 Dự đoán: insert thêm 2 dòng ở nguồn, đích có nhận không và sau bao lâu?
    mysql -h SRC_HOST -u admin -p"$PW" -e "INSERT INTO shop.orders(item,qty) VALUES (\"d\",4),(\"e\",5);"; sleep 30; mysql -h TGT_HOST -u admin -p"$PW" -e "SELECT COUNT(*) FROM shop.orders;"
    Xem kết quảĐích có COUNT(*) = 5 sau vài giây (ví dụ). describe-table-statistics cho thấy Inserts = 2.
  2. Quy trình cutover (paper, thuộc lòng thứ tự):
    1. Xác nhận validation sạch và CDCLatencySource/CDCLatencyTarget (CloudWatch) gần 0.
    2. Dừng ghi vào nguồn (maintenance mode/read-only).
    3. Chờ latency về 0 và đợt thay đổi cuối được apply.
    4. Stop task: aws dms stop-replication-task --replication-task-arn $TASK_ARN.
    5. Tạo phần DMS không chuyển: secondary index, FK, trigger, sequence/auto-increment, user/grant.
    6. Đổi connection string của app (Route 53/Parameter Store) sang đích; test smoke.
    7. Giữ nguồn nguyên trạng một thời gian để rollback, rồi mới tắt.

6Heterogeneous: SCT, DMS Serverless, Snowball, so sánh (paper)

Oracle on-prem → Aurora PostgreSQL: các mảnh ghép và khi nào dùng công cụ nào.

Oracle→ SCT assessment →Schema + code conversion→ apply →Aurora PostgreSQL
Oracle→ DMS full load + CDC →Aurora PostgreSQL
  1. SCT (Schema Conversion Tool): ứng dụng cài trên máy, tạo assessment report (tỷ lệ chuyển tự động, các mục cần sửa tay), chuyển schema, stored procedure, function và SQL trong code ứng dụng. Phần không tự chuyển được phải sửa thủ công. Thay thế không cần cài đặt: DMS Schema Conversion trong console. Thứ tự: SCT/Schema Conversion tạo schema đích → DMS di chuyển dữ liệu (tắt FK/trigger ở đích khi full load, bật lại sau).
  2. 🔮 Dự đoán: bạn chạy DMS full load Oracle → Aurora PostgreSQL mà chưa chuyển schema. Chuyện gì xảy ra?
    Xem kết quảDMS chỉ có thể tạo bảng cơ bản (cột + PK, kiểu dữ liệu ánh xạ mặc định); stored procedure, package, trigger, view phức tạp, sequence không được chuyển. Ứng dụng sẽ hỏng. Đây là lý do đề thi luôn kèm SCT với heterogeneous.
  3. DMS Serverless: DMS tự cấp phát và scale năng lượng (DCU) theo tải, không phải chọn class/instance. Phù hợp tải không đoán được, giảm vận hành. CLI dùng create-replication-config. Có thể đặt min/max capacity.
  4. Fleet Advisor: công cụ khám phá/đánh giá fleet DB. Đã ngừng hỗ trợ ngày 20/05/2026 (không nhận khách mới từ 20/05/2025); AWS đề xuất AWS Migration Evaluator. Có thể vẫn xuất hiện trong tài liệu ôn cũ: biết vai trò, nhưng đừng chọn nó cho dự án mới.
  5. DB cực lớn + băng thông hạn chế: SCT data extraction agent (hoặc dump native) lưu vào Snowball Edge → gửi về AWS → vào S3 → DMS nạp vào đích, rồi CDC bắt kịp thay đổi trong lúc vận chuyển. Snowball Edge chỉ còn cho khách hàng hiện hữu từ 11/2025; khách mới được hướng tới DataSync/Direct Connect/Data Transfer Terminal.
  6. Bảng so sánh các dịch vụ di chuyển hay bị nhầm:
    Dịch vụĐối tượngGhi chú
    DMS (+ SCT)Database (cùng hoặc khác engine)Full load + CDC; SCT cho schema/code
    Native toolsDatabase cùng engineDump/restore, snapshot, replica; downtime dài hơn nhưng đơn giản
    Application Migration Service (MGN)Server/VM (lift-and-shift)Replicate block-level liên tục, cutover bằng test/launch instance; không dành cho chuyển engine DB
    DataSyncFile/object (NFS, SMB, HDFS, S3...)Chuyển dữ liệu online có lịch, verify; không phải CDC cho DB
    Snowball EdgeDữ liệu lớn offlineShip thiết bị; chỉ khách hiện hữu từ 11/2025

7💥 Phá thử

Làm hỏng cố ý để hiểu điều kiện CDC. Phần sandbox yêu cầu đã làm mục 2-4; nếu paper thì chỉ đọc kết quả.

  1. 🔮 Dự đoán: đổi nguồn sang binlog_format=MIXED, rồi tạo task CDC mới. Kết quả?
    aws rds modify-db-parameter-group --db-parameter-group-name sap-dms-src-mysql8 --parameters "ParameterName=binlog_format,ParameterValue=MIXED,ApplyMethod=immediate" aws dms create-replication-task --replication-task-identifier sap-dms-task-bad --source-endpoint-arn $SRC_EP --target-endpoint-arn $TGT_EP --replication-instance-arn $RI_ARN --migration-type cdc --cdc-start-time $(date -u -d "10 minutes ago" +%s) --table-mappings file://tm.json
    Xem kết quảStart task mới sẽ failed với thông báo yêu cầu binlog_format phải là ROW (ví dụ; nội dung chính xác tùy phiên bản). Test connection vẫn có thể thành công, vì lỗi chỉ lộ khi task đọc binlog. Khôi phục: đặt lại ROW. Task cũ đang chạy có thể không phản ánh ngay vì session cũ giữ giá trị cũ; tạo lại kết nối.
  2. 🔮 Dự đoán: nếu RDS nguồn có automated backup retention = 0 thì sao? (Đối chiếu với dms-tgt đã tạo ở mục 2 với retention 0.)
    Xem kết quảKhông có binary log, nên CDC bất khả thi dù parameter group đặt ROW. Full load vẫn chạy được. Đích dms-tgt (retention 0) chỉ là đích nên không sao. Quy tắc: nguồn RDS cho CDC phải có retention > 0.
  3. 🔮 Dự đoán: tạo endpoint với mật khẩu sai rồi test-connection?
    BAD_EP=$(aws dms create-endpoint --endpoint-identifier sap-bad --endpoint-type source --engine-name mysql --server-name SRC_HOST --port 3306 --username admin --password wrongpass --query Endpoint.EndpointArn --output text) aws dms test-connection --replication-instance-arn $RI_ARN --endpoint-arn $BAD_EP > /dev/null; sleep 45 aws dms describe-connections --filters Name=endpoint-arn,Values=$BAD_EP --query "Connections[0].[Status,LastFailureMessage]" --output text
    Xem kết quảfailed kèm thông báo kiểu "Access denied for user" (ví dụ). Trong thực tế lỗi kết nối thường do security group/route, không phải mật khẩu. Test connection là cổng chặn đầu tiên.
  4. 🔮 Dự đoán (paper): bảng không có primary key và dùng full load + CDC thì sao?
    Xem kết quảFull load vẫn chạy nhưng CDC/validation gặp hạn chế: bảng không có PK/unique key không được validate và update/delete trong CDC có thể không áp chính xác (DMS cần khóa để định danh dòng; với MySQL cần bổ sung supplemental info/khóa). Bài học: thêm PK trước khi migrate.

8🧹 Dọn dẹp

Thứ tự: task → endpoint → replication instance → RDS → parameter group → IAM. Replication instance và RDS là phần tốn tiền nhất, xóa ngay khi xong. Bỏ qua nếu chỉ làm paper.

  1. Dừng và xóa task (dừng trước, chờ stopped; endpoint đang gắn task thì không xóa được):
    aws dms stop-replication-task --replication-task-arn $TASK_ARN; aws dms wait replication-task-stopped --filters Name=replication-task-arn,Values=$TASK_ARN for T in $(aws dms describe-replication-tasks --query "ReplicationTasks[].ReplicationTaskArn" --output text); do aws dms delete-replication-task --replication-task-arn $T; done
    Vòng lặp xóa mọi task trong region; chỉ dùng trong sandbox. Task bị failed/ready không cần stop; nếu wait báo lỗi vì task đã dừng, bỏ qua.
  2. Xóa endpoint:
    for E in $(aws dms describe-endpoints --query "Endpoints[?starts_with(EndpointIdentifier,`sap-`)].EndpointArn" --output text); do aws dms delete-endpoint --endpoint-arn $E; done
  3. Xóa replication instance, chờ xóa xong:
    aws dms delete-replication-instance --replication-instance-arn $RI_ARN; aws dms wait replication-instance-deleted --filters Name=replication-instance-id,Values=sap-dms-ri
  4. Xóa 2 RDS (không giữ snapshot/backup), rồi parameter group (chỉ xóa được sau khi instance dùng nó đã bị xóa):
    for D in dms-src dms-tgt; do aws rds delete-db-instance --db-instance-identifier $D --skip-final-snapshot --delete-automated-backups; done aws rds wait db-instance-deleted --db-instance-identifier dms-src; aws rds wait db-instance-deleted --db-instance-identifier dms-tgt aws rds delete-db-parameter-group --db-parameter-group-name sap-dms-src-mysql8
  5. Dọn IAM (nếu bạn đã tạo ở mục 3 và không dùng DMS nữa) và file tạm; tắt EC2 có mysql client nếu đã tạo:
    aws iam detach-role-policy --role-name dms-vpc-role --policy-arn arn:aws:iam::aws:policy/service-role/AmazonDMSVPCManagementRole; aws iam delete-role --role-name dms-vpc-role; rm -f tm.json ts.json
  6. Xác nhận: aws dms describe-replication-instances và aws rds describe-db-instances không còn tài nguyên lab.

9🎯 3 câu hỏi kiểu đề

Tự suy nghĩ trước, rồi mở đáp án.

Câu 1

Một công ty chạy PostgreSQL 14 on-prem (1.5 TB) và cần chuyển sang Amazon Aurora PostgreSQL. Ứng dụng chỉ chịu được downtime vài phút. Có Site-to-Site VPN ổn định 1 Gbps. Giải pháp nào phù hợp nhất?

  1. Dùng AWS DMS với migration type full-load, ngừng ứng dụng trong lúc copy.
  2. Dùng AWS DMS với full-load-and-cdc, rồi cutover khi replication lag gần 0.
  3. Dùng AWS DataSync để copy file dữ liệu của PostgreSQL sang Aurora.
  4. Dùng AWS MGN để replicate máy chủ DB sang EC2 rồi đổi sang Aurora.
Xem đáp ánB. Cùng engine, cần downtime tối thiểu, băng thông đủ: full load + CDC. A gây downtime dài. DataSync chuyển file, không biết cấu trúc DB để nạp vào Aurora (C sai). MGN chuyển server thành EC2, không tạo ra Aurora (D sai).

Câu 2

Công ty muốn chuyển cơ sở dữ liệu Oracle có nhiều package PL/SQL sang Aurora PostgreSQL. Đội ngũ chạy thử DMS full load và thấy dữ liệu sang nhưng ứng dụng báo thiếu hàm và procedure. Cần làm gì?

  1. Tăng kích thước replication instance và chạy lại.
  2. Bật validation trong task settings.
  3. Dùng AWS SCT (hoặc DMS Schema Conversion) để chuyển schema và code, xử lý thủ công phần không tự chuyển được, rồi dùng DMS để di chuyển dữ liệu.
  4. Chuyển sang CDC-only để DMS tự tạo procedure từ redo log.
Xem đáp ánC. DMS di chuyển dữ liệu, không chuyển code đối tượng khác engine. Kích thước instance (A) và validation (B) không giải quyết thiếu code. CDC (D) chỉ đồng bộ thay đổi dữ liệu.

Câu 3

Task DMS full-load-and-cdc từ RDS for MySQL nguồn đã chạy full load thành công, nhưng giai đoạn CDC liên tục thất bại. Nhật ký cho thấy binary log không khả dụng. Nguồn là RDS với automated backups tắt. Nguyên nhân và cách sửa nào đúng?

  1. Thiếu quyền IAM cho DMS; gắn thêm AmazonRDSFullAccess.
  2. Bật automated backups (retention > 0) để RDS ghi binlog, đặt binlog_format=ROW, tăng binlog retention rồi chạy lại.
  3. Chuyển target sang Aurora Serverless.
  4. Đổi task thành full-load để tránh dùng binlog.
Xem đáp ánB. RDS chỉ bật binary log khi automated backup retention > 0; CDC của MySQL đọc binlog, cần ROW. IAM (A) không liên quan đến việc đọc binlog trong DB; đổi target (C) không ảnh hưởng nguồn; D bỏ mất yêu cầu đồng bộ liên tục.

10📌 Quy tắc ghi nhớ

  1. Downtime tối thiểu = full-load-and-cdc; cutover khi lag ~0; CDC MySQL cần binlog ROW và RDS backup retention > 0.
  2. Khác engine = SCT (hoặc DMS Schema Conversion) cho schema/code + DMS cho dữ liệu; DMS chỉ tạo bảng và PK, index/FK/trigger làm riêng.
  3. Endpoint phải Test connection thành công từ replication instance; lỗi thường là security group/route.
  4. DB rất lớn + băng thông yếu: seed offline (Snowball Edge/backup) rồi DMS CDC; cùng engine, chịu downtime: native tools thường đủ.
  5. DMS = database; MGN = server; DataSync = file/object; Fleet Advisor đã ngừng (dùng Migration Evaluator).
Lab tự biên soạn cho ôn thi AWS SAP-C02. Kết quả mẫu ghi "ví dụ"; một số dịch vụ (Fleet Advisor, Snowball Edge) đã thay đổi khả dụng, hãy kiểm tra lại tài liệu AWS.
