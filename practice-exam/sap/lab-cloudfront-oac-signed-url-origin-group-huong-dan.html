Tổng quan & kịch bản

Phân phối nội dung private từ S3 qua CloudFront: chỉ CloudFront đọc được bucket (OAC), chỉ người có chữ ký mới tải được (signed URL/cookies), và tự failover sang bucket ở region khác (origin group).

Công ty bán khoá học online. File nằm trong S3 bucket private; người dùng chỉ được tải qua CloudFront. Một số file cần link tạm thời (signed URL), thư mục video nhiều file cần cookie (signed cookies). Để chịu lỗi region, có bucket phụ ở region khác, CloudFront tự chuyển sang đó khi bucket chính lỗi.

Viewer>URL ký / cookie ký →CloudFront
key group + OAC>SigV4 (OAC) →S3 primary
ap-southeast-1>lỗi 403/5xx →S3 secondary
ap-northeast-1
RegionPrimary ap-southeast-1, Secondary ap-northeast-1 (CloudFront là dịch vụ global)
Tài nguyên2 S3 bucket, 1 OAC, 1 public key + key group, 1 distribution (2 origin + 1 origin group)
Công cụAWS CLI v2, openssl, jq, curl; console cho phần cấu hình distribution
Thời giankhoảng 35-40 phút, trong đó mỗi lần deploy distribution mất vài phút (thường 3-10 phút; trạng thái Deploying → Last modified có ngày). Lab thiết kế chỉ 2 lần deploy cộng 1 lần khi phá thử và 1 lần khi dọn dẹp.
Chi phíRất thấp (vài cent: S3 + request; CloudFront có free tier). Vẫn dọn dẹp để tránh để lại distribution.
Liên hệ đề thi (SAP-C02) — lab này sửa các bẫy:
• OAC thay OAI; bucket policy principal là cloudfront.amazonaws.com + AWS:SourceArn; OAC không dùng được với S3 website endpoint.
• Signed URL (một file) vs signed cookies (nhiều file, không đổi URL); dùng trusted key group thay vì root key pair.
• Origin group chỉ failover cho GET/HEAD/OPTIONS; S3 thiếu object thường trả 403 (không phải 404) nên phải chọn 403.
• CloudFront Functions vs Lambda@Edge; Geo restriction chỉ ở mức quốc gia.
Mẹo: giữ một shell cho cả lab. Các biến chính: $ACCT $B1 $B2 $KID $KG $OAC $DIST $DOMAIN.

1Tạo 2 S3 bucket private ở 2 region

Bucket mới tạo giữ nguyên Block Public Access (bật cả 4 cờ). Không mở public để bật CloudFront.

  1. Chạy script tạo bucket + upload file:
    export AWS_REGION=ap-southeast-1
ACCT=$(aws sts get-caller-identity --query Account --output text)
B1=lab-cf-primary-$ACCT      # ap-southeast-1
B2=lab-cf-secondary-$ACCT    # ap-northeast-1

aws s3api create-bucket --bucket $B1 --region ap-southeast-1 --create-bucket-configuration LocationConstraint=ap-southeast-1
aws s3api create-bucket --bucket $B2 --region ap-northeast-1 --create-bucket-configuration LocationConstraint=ap-northeast-1

# Block Public Access mặc định đã bật cho bucket mới; xác nhận:
aws s3api get-public-access-block --bucket $B1

# Nội dung khác nhau để biết đang nhận từ bucket nào
echo "<h1>PRIMARY (ap-southeast-1)</h1>"   > index-p.html
echo "<h1>SECONDARY (ap-northeast-1)</h1>" > index-s.html
echo "b.txt from PRIMARY"   > b-p.txt
echo "b.txt from SECONDARY" > b-s.txt
echo "only in SECONDARY"    > only-secondary.txt

aws s3 cp index-p.html s3://$B1/index.html --content-type text/html
aws s3 cp index-s.html s3://$B2/index.html --content-type text/html
aws s3 cp b-p.txt s3://$B1/b.txt
aws s3 cp b-s.txt s3://$B2/b.txt
aws s3 cp only-secondary.txt s3://$B2/only-secondary.txt
    🔮 Dự đoán: Truy cập trực tiếp https://$B1.s3.ap-southeast-1.amazonaws.com/index.html bằng curl sẽ ra gì?
    Xem kết quảcurl -s -o /dev/null -w '%{http_code}\n' https://$B1.s3.ap-southeast-1.amazonaws.com/index.html → 403 (AccessDenied). Đây là trạng thái mong muốn: bucket private. (ví dụ: 403)
  2. Lưu ý only-secondary.txt chỉ có ở bucket phụ — dùng để thấy failover ở mục 6, còn b.txt có ở cả hai.

2Chuẩn bị khoá (key group) và OAC

Tạo cặp khoá RSA 2048, đăng ký public key vào CloudFront, gom vào trusted key group; tạo Origin Access Control.

  1. Tạo khoá, public key, key group:
    openssl genrsa -out private_key.pem 2048
openssl rsa -pubout -in private_key.pem -out public_key.pem

jq -n --arg k "$(cat public_key.pem)" '{CallerReference:"lab-cf-1",Name:"lab-pubkey",EncodedKey:$k}' > pk-config.json
KID=$(aws cloudfront create-public-key --public-key-config file://pk-config.json --query PublicKey.Id --output text)

jq -n --arg id "$KID" '{Name:"lab-keygroup",Items:[$id]}' > kg-config.json
KG=$(aws cloudfront create-key-group --key-group-config file://kg-config.json --query KeyGroup.Id --output text)
echo "KID=$KID KG=$KG"
    Key group dùng RSA 2048-bit. Giữ private key bí mật (không commit/không upload S3). Cách cũ 'trusted signers' dựa trên CloudFront key pair của root user — AWS khuyến nghị dùng key group vì không cần root và quản lý được qua IAM.
  2. Tạo OAC (SigningBehavior=always: CloudFront luôn ký SigV4 request gửi tới S3):
    OAC=$(aws cloudfront create-origin-access-control --origin-access-control-config \
  Name=lab-oac,SigningProtocol=sigv4,SigningBehavior=always,OriginAccessControlOriginType=s3 \
  --query OriginAccessControl.Id --output text)
echo $OAC
    🔮 Dự đoán: OAC khác OAI chỗ nào về cách S3 nhận diện CloudFront?
    Xem kết quảOAI: S3 nhận một 'user' đặc biệt (CanonicalUser/OAI ID) trong bucket policy. OAC: principal là service principal cloudfront.amazonaws.com và giới hạn bằng điều kiện AWS:SourceArn = ARN distribution. OAC hỗ trợ SSE-KMS, mọi region, và request PUT/DELETE; OAI thì không.

3Distribution lần 1: OAC, chưa hạn chế người xem

Tạo distribution trỏ vào bucket primary bằng OAC; xác nhận chỉ đi qua CloudFront mới đọc được. (Deploy lần 1)

  1. Console → CloudFront → Create distribution. Origin domain = bucket lab-cf-primary-<ACCT> (chọn dạng S3 REST endpoint …s3.ap-southeast-1.amazonaws.com, không phải website endpoint). Nếu console hỏi plan, chọn Pay-as-you-go/Free; giao diện có thể khác chút giữa các phiên bản.
    Mục Origin access: chọn Origin access control settings (recommended) → chọn OAC lab-oac có sẵn. Console sẽ gợi ý bucket policy — bỏ qua, ta tự đặt ở bước sau.
  2. Viewer protocol policy = Redirect HTTP to HTTPS; Allowed methods = GET, HEAD; Cache policy = CachingOptimized; Default root object = index.html; Description = lab-cf (để lọc bằng CLI); WAF: tắt cho tiết kiệm. Bấm Create distribution.
  3. Lấy ID/domain bằng CLI:
    DIST=$(aws cloudfront list-distributions --query "DistributionList.Items[?Comment=='lab-cf'].Id | [0]" --output text)
DOMAIN=$(aws cloudfront get-distribution --id $DIST --query Distribution.DomainName --output text)
echo $DIST $DOMAIN
aws cloudfront wait distribution-deployed --id $DIST && echo DEPLOYED
    Chờ deploy: lệnh wait chặn terminal vài phút (đang đợi ~3-10 phút). Trong lúc đó làm tiếp bước kế (bucket policy) ở tab khác.
  4. Áp bucket policy OAC cho primary (làm lúc distribution đang deploy cũng được):
    cat > policy-primary.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": {"Service": "cloudfront.amazonaws.com"},
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::$B1/*",
    "Condition": {"StringEquals": {"AWS:SourceArn": "arn:aws:cloudfront::$ACCT:distribution/$DIST"}}
  }]
}
EOF
jq . policy-primary.json >/dev/null && aws s3api put-bucket-policy --bucket $B1 --policy file://policy-primary.json
    Policy cấp s3:GetObject cho service CloudFront nhưng chỉ khi request đến từ đúng distribution này (confused-deputy protection). Block Public Access vẫn bật — policy này không phải public vì principal là service + điều kiện SourceArn. Không cấp s3:ListBucket nên object không tồn tại sẽ trả 403, không phải 404.
  5. Test khi đã DEPLOYED:
    curl -s https://$DOMAIN/index.html
curl -s -o /dev/null -w '%{http_code}\n' https://$B1.s3.ap-southeast-1.amazonaws.com/index.html
curl -s -o /dev/null -w '%{http_code}\n' https://$DOMAIN/khong-co.html
    🔮 Dự đoán: Ba lệnh lần lượt in gì?
    Xem kết quả1) <h1>PRIMARY (ap-southeast-1)</h1> — qua CloudFront đọc được. 2) 403 — truy cập thẳng S3 bị chặn. 3) 403 (ví dụ) — object không tồn tại cũng là 403 vì thiếu ListBucket. Nếu bước 1 ra AccessDenied XML: bucket policy sai ARN/ID distribution hoặc chưa có hiệu lực.

4Bắt buộc ký: key group + signed URL + signed cookies

Sửa behavior mặc định: Restrict viewer access = Yes (key group). Đồng thời thêm origin secondary + origin group ở mục 5 để chỉ tốn 1 lần deploy.

  1. Console → distribution → tab Behaviors → chọn Default (*) → Edit → Restrict viewer access = Yes, Trusted authorization type = Trusted key groups, chọn lab-keygroup. Chưa Save — làm tiếp mục 5 (thêm origin group) rồi Save một lần để chỉ tốn một lần deploy; các bước test 2-4 dưới đây chạy sau khi deploy đó xong.
  2. (Sau khi deploy xong) Thử không ký:
    curl -s https://$DOMAIN/index.html
    🔮 Dự đoán: Request không có chữ ký thì CloudFront trả gì?
    Xem kết quảHTTP 403 với XML dạng <Code>MissingKey</Code> Missing Key-Pair-Id query parameter or cookie value (ví dụ). CloudFront chặn ngay ở edge, không hỏi S3.
  3. Signed URL bằng aws cloudfront sign (canned policy):
    # Ký URL cho một file (canned policy), hết hạn sau 1 giờ
aws cloudfront sign --url https://$DOMAIN/index.html --key-pair-id $KID \
  --private-key file://private_key.pem --date-less-than $(date -u -d '+1 hour' +%Y-%m-%dT%H:%M:%S)
    🔮 Dự đoán: Lệnh in ra gì? Dùng URL đó với curl được không, và còn dùng được khi đổi path sang /b.txt không?
    Xem kết quảIn URL gốc kèm ?Expires=…&Signature=…&Key-Pair-Id=K… (ví dụ: https://dxxxx.cloudfront.net/index.html?Expires=1790000000&Signature=Ab…~&Key-Pair-Id=K2ABC…). curl URL đó (đặt trong dấu nháy kép) → 200. Đổi path sang /b.txt → 403, vì chữ ký gắn với đúng một URL (canned policy). Muốn wildcard phải dùng custom policy (--policy trong thư viện/CLI khác, không có ở aws cloudfront sign bản đơn giản).
  4. Signed cookies cho nhiều file: dùng custom policy với wildcard /*.
    EXP=$(date -d '+1 hour' +%s)
POLICY=$(jq -cn --arg r "https://$DOMAIN/*" --argjson e $EXP '{Statement:[{Resource:$r,Condition:{DateLessThan:{"AWS:EpochTime":$e}}}]}')
b64() { openssl base64 -A | tr '+=/' '-_~'; }
CF_POLICY=$(printf %s "$POLICY" | b64)
CF_SIG=$(printf %s "$POLICY" | openssl dgst -sha1 -sign private_key.pem | b64)

# Một cookie jar dùng cho nhiều file: không cần sửa URL
curl -s -o /dev/null -w '%{http_code}\n' -H "Cookie: CloudFront-Policy=$CF_POLICY; CloudFront-Signature=$CF_SIG; CloudFront-Key-Pair-Id=$KID" https://$DOMAIN/index.html
curl -s -H "Cookie: CloudFront-Policy=$CF_POLICY; CloudFront-Signature=$CF_SIG; CloudFront-Key-Pair-Id=$KID" https://$DOMAIN/b.txt
    🔮 Dự đoán: Hai lệnh curl in gì? Điểm khác chính so với signed URL?
    Xem kết quả200 rồi nội dung b.txt from PRIMARY (ví dụ). Một bộ cookie phủ mọi file khớp https://$DOMAIN/*, URL không đổi — hợp cho HLS/DASH (manifest + hàng nghìn segment) hoặc cả khu vực 'members'. Trình duyệt thật cần backend set 3 cookie CloudFront-Policy, CloudFront-Signature, CloudFront-Key-Pair-Id (cùng domain hoặc CNAME).
  5. Bảng chọn nhanh:
    Một file (download, link email)Signed URL
    Client không hỗ trợ cookie (một số player/ứng dụng)Signed URL
    Nhiều file, không muốn đổi URL (HLS, thư mục)Signed cookies
    Giới hạn IP/ngày bắt đầuCustom policy (cả URL lẫn cookies)

5Origin group: failover primary → secondary

Thêm origin bucket phụ (cùng OAC), gom thành origin group, trỏ behavior vào group. (Deploy lần 2, gộp với bước hạn chế người xem ở mục 4)

  1. Áp bucket policy OAC cho secondary (cùng distribution ARN, vì cùng một distribution đọc cả hai bucket):
    cat > policy-secondary.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": {"Service": "cloudfront.amazonaws.com"},
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::$B2/*",
    "Condition": {"StringEquals": {"AWS:SourceArn": "arn:aws:cloudfront::$ACCT:distribution/$DIST"}}
  }]
}
EOF
jq . policy-secondary.json >/dev/null && aws s3api put-bucket-policy --bucket $B2 --policy file://policy-secondary.json
  2. Console → distribution → tab Origins → Create origin: Origin domain = bucket secondary (…s3.ap-northeast-1.amazonaws.com), Origin access = OAC lab-oac → Create.
  3. Vẫn ở tab Origins → Create origin group: Name og-lab; Origins = thêm primary trước, secondary sau (thứ tự = ưu tiên); Failover criteria chọn 403, 404, 500, 502, 503, 504 → Create.
    Origin group cần ≥2 origin. Failover xảy ra khi origin chính trả đúng các mã đã chọn (hoặc lỗi kết nối/timeout). Các mã có thể chọn: 400, 403, 404, 416, 500, 502, 503, 504.
  4. Tab Behaviors → sửa Default (*): Origin and origin groups = og-lab; hoàn tất cấu hình hạn chế viewer ở mục 4 (key group); Save changes. Chờ deploy:
    aws cloudfront wait distribution-deployed --id $DIST && echo DEPLOYED
    Đây là lần deploy thứ 2 — vài phút. Allowed methods của behavior dùng origin group phải là GET, HEAD (hoặc kèm OPTIONS); failover không áp dụng cho POST/PUT/DELETE.
  5. Test failover (cần cookie từ mục 4; nếu hết hạn hãy tạo lại):
    aws cloudfront create-invalidation --distribution-id $DIST --paths "/*" >/dev/null   # đảm bảo không dính cache cũ
# Cookie đã tạo ở mục 4 (CF_POLICY, CF_SIG, KID) vẫn dùng được:
H="Cookie: CloudFront-Policy=$CF_POLICY; CloudFront-Signature=$CF_SIG; CloudFront-Key-Pair-Id=$KID"
curl -s -H "$H" https://$DOMAIN/index.html
curl -s -H "$H" https://$DOMAIN/only-secondary.txt
    🔮 Dự đoán: File đầu tiên đến từ bucket nào? File only-secondary.txt không có ở primary, vậy kết quả?
    Xem kết quả1) <h1>PRIMARY (ap-southeast-1)</h1> — origin chính còn sống thì dùng nó. 2) only in SECONDARY — primary trả 403 (thiếu object + không có ListBucket) → CloudFront thử secondary và thành công. Nếu bạn quên chọn 403 trong failover criteria, bước này sẽ trả 403 thẳng cho viewer: đúng bẫy hay gặp.

6So sánh: OAC vs OAI vs website endpoint; Functions vs Lambda@Edge; Geo restriction

Phần kiến thức bổ sung, có một thử nghiệm geo ở mục 7.

6A. S3 origin: OAC, OAI, website endpoint

CáchĐặc điểmDùng cho
OAC (nên dùng)Service principal cloudfront.amazonaws.com + AWS:SourceArn; SigV4; hỗ trợ SSE-KMS (key policy cho phép CloudFront), mọi region, PUT/DELETES3 REST endpoint
OAI (legacy)Principal là OAI; chỉ SSE-S3, không hỗ trợ opt-in region/ SSE-KMS; AWS khuyên chuyển sang OACS3 REST endpoint
S3 website endpointLà custom origin (HTTP-only); không dùng được OAC/OAI. Muốn hạn chế truy cập: bucket public hạn chế bằng header bí mật (Referer hoặc custom header) — kém an toànCần redirect/index doc kiểu website
Custom origin (ALB/EC2/API)Dùng custom header bí mật + SG dùng prefix list CloudFront để giới hạn nguồnOrigin không phải S3
Bẫy kinh điển: 'bucket bật Static website hosting + yêu cầu chỉ CloudFront truy cập qua OAC' → không thực hiện được trực tiếp. Giải pháp: chuyển origin sang REST endpoint với OAC, dùng default root object hoặc CloudFront Function để rewrite /dir/ → /dir/index.html.

6C. Geo restriction

Cấu hình ở Security → CloudFront geographic restrictions: allow list hoặc block list theo quốc gia, áp cho cả distribution (không theo behavior), viewer bị chặn nhận 403. Cần mịn hơn (bang/thành phố, theo path) → dùng AWS WAF geo match, hoặc header CloudFront-Viewer-Country kết hợp Function/Lambda@Edge, hoặc dịch vụ geolocation bên thứ ba kết hợp signed URL.

7💥 Phá thử

Làm hỏng có chủ đích để thấy chính xác cách CloudFront/S3 phản ứng.

  1. Signed URL hết hạn.
    OLD=$(aws cloudfront sign --url https://$DOMAIN/index.html --key-pair-id $KID --private-key file://private_key.pem --date-less-than $(date -u -d '-1 hour' +%Y-%m-%dT%H:%M:%S))
curl -s -o /dev/null -w '%{http_code}\n' "$OLD"
    🔮 Dự đoán: Chữ ký hợp lệ nhưng đã quá hạn. Mã trả về?
    Xem kết quả403 (thông điệp kiểu Access denied, ví dụ). Chữ ký đúng không đủ — thời gian hiệu lực cũng được kiểm tra.
  2. Làm hỏng primary: xoá bucket policy để CloudFront mất quyền đọc, rồi hỏi file chưa cache là b.txt:
    aws s3api delete-bucket-policy --bucket $B1
sleep 5
curl -s -H "$H" https://$DOMAIN/b.txt
    🔮 Dự đoán: b.txt chưa từng được request qua distribution này sau lần invalidate. Bucket primary giờ trả 403 → viewer thấy gì? Còn /index.html (đã cache)?
    Xem kết quảb.txt from SECONDARY — failover thành công vì 403 nằm trong criteria. /index.html vẫn ra PRIMARY nếu còn cache (TTL mặc định 24h): cache che lỗi origin, và response lấy từ secondary cũng được cache. Khôi phục: aws s3api put-bucket-policy --bucket $B1 --policy file://policy-primary.json rồi invalidate /*.
  3. Bỏ 403 khỏi failover criteria (console: Origins → og-lab → Edit, chỉ giữ 500/502/503/504 → deploy) rồi request /only-secondary.txt (chưa cache).
    🔮 Dự đoán: Không còn failover cho 403. Kết quả?
    Xem kết quả403 trả thẳng cho viewer, dù secondary có file. Bài học: S3 + OAC thiếu quyền/thiếu object = 403, nên origin group cho S3 thường phải gồm 403 (và có thể 404). Khôi phục lại criteria nếu muốn tiếp tục.
  4. Geo restriction (tuỳ chọn, thêm 1 lần deploy): Security → CloudFront geographic restrictions → Block list → chọn quốc gia của bạn (ví dụ Vietnam), Save, đợi deploy, curl kèm cookie.
    🔮 Dự đoán: Request đã ký hợp lệ nhưng đến từ quốc gia bị chặn. Kết quả?
    Xem kết quả403 với thông điệp kiểu The Amazon CloudFront distribution is configured to block access from your country (ví dụ). Chữ ký đúng không vượt được geo restriction. Gỡ block list sau khi thử (hoặc bỏ qua vì dọn dẹp sẽ xoá distribution).
  5. Truy cập thẳng S3 / website endpoint đã làm ở mục 3 (403). Lý thuyết cần nhớ: nếu bạn bật Static website hosting và chọn website endpoint làm origin, console coi là custom origin và không có tuỳ chọn OAC.

8🧹 Dọn dẹp

Thứ tự: disable distribution → chờ deploy → xoá distribution → key group/public key/OAC → bucket.

# 1) Tắt distribution (phải Disabled trước khi xoá)
aws cloudfront get-distribution-config --id $DIST > dist-cfg.json
ETAG=$(jq -r .ETag dist-cfg.json)
jq '.DistributionConfig | .Enabled=false' dist-cfg.json > dist-off.json
aws cloudfront update-distribution --id $DIST --if-match "$ETAG" --distribution-config file://dist-off.json >/dev/null

# 2) Chờ deploy xong (vài phút), rồi xoá distribution với ETag MỚI
aws cloudfront wait distribution-deployed --id $DIST
ETAG=$(aws cloudfront get-distribution --id $DIST --query ETag --output text)
aws cloudfront delete-distribution --id $DIST --if-match "$ETAG"

# 3) Xoá key group TRƯỚC, rồi public key, rồi OAC (chỉ xoá được khi không còn distribution tham chiếu)
aws cloudfront delete-key-group --id $KG --if-match "$(aws cloudfront get-key-group --id $KG --query ETag --output text)"
aws cloudfront delete-public-key --id $KID --if-match "$(aws cloudfront get-public-key --id $KID --query ETag --output text)"
aws cloudfront delete-origin-access-control --id $OAC --if-match "$(aws cloudfront get-origin-access-control --id $OAC --query ETag --output text)"

# 4) Làm rỗng và xoá 2 bucket
aws s3 rm s3://$B1 --recursive && aws s3api delete-bucket --bucket $B1 --region ap-southeast-1
aws s3 rm s3://$B2 --recursive && aws s3api delete-bucket --bucket $B2 --region ap-northeast-1

# 5) File cục bộ (đặc biệt private key)
rm -f private_key.pem public_key.pem pk-config.json kg-config.json dist-cfg.json dist-off.json policy-*.json index-*.html b-*.txt only-secondary.txt
Distribution phải ở trạng thái Disabled và đã deploy xong thì mới xoá được; nếu không sẽ gặp lỗi DistributionNotDisabled. Xoá key group khi distribution còn tồn tại sẽ báo lỗi vì đang được tham chiếu. Nếu delete-distribution báo PreconditionFailed: ETag cũ — lấy lại ETag bằng get-distribution.

9🎯 3 câu hỏi kiểu đề

Tự đặt, không lấy từ bộ đề nào.

Câu 1

Một nền tảng học trực tuyến lưu video HLS (một file manifest và hàng nghìn segment .ts) trong S3 bucket private. Chỉ người đã đăng nhập được xem; manifest chứa đường dẫn tương đối nên không được đổi URL. Giải pháp bảo mật và ít sửa code nhất?

  1. Tạo S3 presigned URL cho từng segment và ghi lại vào manifest.
  2. Dùng CloudFront với OAC cho bucket và phát signed cookies (trusted key group) sau khi đăng nhập.
  3. Dùng CloudFront signed URL cho manifest; segment để public.
  4. Đặt bucket public và dùng AWS WAF giới hạn theo IP.
Xem đáp án

Đáp án: B

Nhiều file và không đổi URL → signed cookies; OAC giữ bucket private. A/C buộc đổi URL hoặc làm lộ segment. D không xác thực được từng người dùng.

Câu 2

Một bucket S3 bật Static website hosting (cần index document và redirect rule). Team muốn đặt CloudFront phía trước và đảm bảo người dùng không bypass CloudFront để vào thẳng S3, dùng OAC. Điều nào đúng?

  1. Gắn OAC vào origin là website endpoint rồi thêm bucket policy với AWS:SourceArn.
  2. OAC không hỗ trợ website endpoint; chuyển origin sang S3 REST endpoint với OAC, và xử lý index document bằng default root object/CloudFront Function.
  3. Dùng OAI cho website endpoint vì OAI hỗ trợ.
  4. Bật Block Public Access, website endpoint vẫn hoạt động bình thường với CloudFront.
Xem đáp án

Đáp án: B

Website endpoint là custom origin (HTTP), không dùng OAC/OAI; Block Public Access sẽ làm website endpoint không phục vụ được. Dùng REST endpoint + OAC rồi rewrite bằng default root object hoặc CloudFront Function.

Câu 3

Ứng dụng phục vụ file tĩnh từ bucket S3 chính (ap-southeast-1), được sao chép sang bucket DR (eu-west-1). Với OAC, khi một object chưa tồn tại hoặc bucket chính gặp sự cố quyền, viewer nhận lỗi 403 trong khi bản sao có file. Cần tự động chuyển sang DR cho request GET mà không đổi DNS. Cấu hình nào đúng?

  1. Origin group (primary → DR) với failover criteria chỉ gồm 500, 502, 503, 504.
  2. Origin group (primary → DR) với failover criteria gồm cả 403 (và 404), behavior chỉ cho GET/HEAD.
  3. Route 53 failover record trước CloudFront với health check vào endpoint S3.
  4. Lambda@Edge viewer-request đổi origin khi nhận được lỗi.
Xem đáp án

Đáp án: B

S3 thiếu object hoặc không đủ quyền với OAC trả 403 nên phải đưa 403 vào criteria; origin group chỉ failover cho GET/HEAD/OPTIONS. A bỏ sót 403. C tăng độ phức tạp và không dựa vào mã lỗi theo request. D: viewer-request chạy trước khi biết origin lỗi, không phù hợp.

10📌 Quy tắc ghi nhớ

  • OAC > OAI: principal cloudfront.amazonaws.com + AWS:SourceArn; OAC chỉ cho S3 REST endpoint, không cho website endpoint.
  • 1 file → signed URL; nhiều file/giữ URL → signed cookies; dùng trusted key group, không dùng root key pair.
  • Origin group: ≥2 origin, chỉ failover GET/HEAD/OPTIONS; S3 + OAC thiếu object = 403 → nhớ chọn 403.
  • CloudFront Functions = viewer events, <1ms, không network; Lambda@Edge = 4 events, tạo ở us-east-1, nặng hơn.
  • Geo restriction = cấp quốc gia, toàn distribution, trả 403; muốn mịn hơn dùng WAF/Function.
