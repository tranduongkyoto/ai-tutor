Tổng quan & kịch bản

Hybrid DNS: VPC phân giải tên on-prem (corp.example) và on-prem phân giải tên trong Private Hosted Zone (aws.example).

Công ty có data center on-prem nối với AWS (Direct Connect/VPN). Yêu cầu: workload trong VPC gọi được app.corp.example (DNS do on-prem quản lý) và server on-prem gọi được web.aws.example (record nằm trong Route 53 Private Hosted Zone). Lab này giả lập on-prem bằng VPC thứ hai chạy dnsmasq trên EC2 Amazon Linux 2023, nối với VPC chính qua VPC peering (thay cho Direct Connect/VPN).

Thời giankhoảng 35-40 phút (endpoint mất 3-6 phút để lên OPERATIONAL)
Chi phí: mỗi IP address (ENI) của Resolver endpoint tính khoảng $0.125/giờ (kiểm tra lại trang pricing). Lab tạo 2 endpoint × 2 IP = 4 ENI ≈ $0.5/giờ, chưa kể EC2 và phí query. Làm liền một mạch rồi dọn dẹp ngay (mục 8).
Liên hệ đề thi (SAP-C02) — lab này sửa các bẫy:
• Inbound vs Outbound: inbound = on-prem → AWS; outbound = AWS → on-prem (hay bị đảo).
• Endpoint cần ≥ 2 IP ở 2 AZ và security group mở 53 TCP + UDP.
• PHZ chỉ hoạt động khi VPC bật enableDnsSupport + enableDnsHostnames.
• Chia sẻ forwarding rule qua RAM (không chia sẻ được endpoint); PHZ khác account dùng association authorization.
• Đáp án 'EC2 BIND forwarder' là kiểu cũ: nhiều vận hành hơn Resolver endpoint.
Mẹo: giữ một shell cho cả lab (biến như $CLOUD, $SG_IN dùng xuyên suốt). Để phòng mất shell, chạy lệnh lưu biến ở bước 1.9 rồi source ~/lab-r53.env khi mở shell mới.

1Dựng mạng: 2 VPC + peering + security group

VPC 'cloud' (nơi đặt Resolver endpoint) và VPC 'on-prem' nối với nhau bằng VPC peering.

1A. VPC, subnet, IGW, peering (CLI)

  1. Mở terminal đã cấu hình AWS CLI v2 (aws sts get-caller-identity chạy được). Dán đoạn script dưới (chạy trong cùng một shell):
    export AWS_REGION=ap-southeast-1 AWS_DEFAULT_REGION=ap-southeast-1
AZ_A=ap-southeast-1a; AZ_B=ap-southeast-1b

# VPC cloud + VPC on-prem
CLOUD=$(aws ec2 create-vpc --cidr-block 10.0.0.0/16 --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=lab-cloud}]' --query Vpc.VpcId --output text)
ONPREM=$(aws ec2 create-vpc --cidr-block 10.1.0.0/16 --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=lab-onprem}]' --query Vpc.VpcId --output text)
for V in $CLOUD $ONPREM; do
  aws ec2 modify-vpc-attribute --vpc-id $V --enable-dns-support '{"Value":true}'
  aws ec2 modify-vpc-attribute --vpc-id $V --enable-dns-hostnames '{"Value":true}'
done

# Subnets
SUB_A=$(aws ec2 create-subnet --vpc-id $CLOUD --cidr-block 10.0.1.0/24 --availability-zone $AZ_A --query Subnet.SubnetId --output text)
SUB_B=$(aws ec2 create-subnet --vpc-id $CLOUD --cidr-block 10.0.2.0/24 --availability-zone $AZ_B --query Subnet.SubnetId --output text)
SUB_ON=$(aws ec2 create-subnet --vpc-id $ONPREM --cidr-block 10.1.1.0/24 --availability-zone $AZ_A --query Subnet.SubnetId --output text)

# Internet gateway cho cả 2 VPC (chỉ để cài dnsmasq + Session Manager)
for V in $CLOUD $ONPREM; do
  IGW=$(aws ec2 create-internet-gateway --query InternetGateway.InternetGatewayId --output text)
  aws ec2 attach-internet-gateway --internet-gateway-id $IGW --vpc-id $V
  RT=$(aws ec2 describe-route-tables --filters Name=vpc-id,Values=$V Name=association.main,Values=true --query 'RouteTables[0].RouteTableId' --output text)
  aws ec2 create-route --route-table-id $RT --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW >/dev/null
  [ $V = $CLOUD ] && { RT_C=$RT; IGW_C=$IGW; } || { RT_O=$RT; IGW_O=$IGW; }
done

# VPC peering + route 2 chiều
PCX=$(aws ec2 create-vpc-peering-connection --vpc-id $CLOUD --peer-vpc-id $ONPREM --query VpcPeeringConnection.VpcPeeringConnectionId --output text)
aws ec2 accept-vpc-peering-connection --vpc-peering-connection-id $PCX >/dev/null
aws ec2 create-route --route-table-id $RT_C --destination-cidr-block 10.1.0.0/16 --vpc-peering-connection-id $PCX >/dev/null
aws ec2 create-route --route-table-id $RT_O --destination-cidr-block 10.0.0.0/16 --vpc-peering-connection-id $PCX >/dev/null
    Hai VPC đều bật enableDnsSupport và enableDnsHostnames — VPC mới tạo bằng CLI mặc định chỉ bật DNS support, còn hostnames mặc định tắt, nên phải bật tay. Hai điều kiện này là bắt buộc để Private Hosted Zone hoạt động.
    🔮 Dự đoán: Sau khi chạy, peering ở trạng thái gì? Có cần bật 'DNS resolution from accepter VPC' trên peering để lab chạy không?
    Xem kết quảTrạng thái active (kiểm tra: aws ec2 describe-vpc-peering-connections --vpc-peering-connection-ids $PCX --query 'VpcPeeringConnections[0].Status.Code'). Không cần bật DNS resolution của peering: DNS ở đây đi bằng IP của endpoint/dnsmasq qua route, không dùng tên private DNS qua peering.
  2. Tạo security group (4 cái):
    # SG cho inbound endpoint: on-prem (10.1.0.0/16) được hỏi DNS vào endpoint
SG_IN=$(aws ec2 create-security-group --group-name lab-r53-inbound --description "R53 inbound endpoint" --vpc-id $CLOUD --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SG_IN --ip-permissions \
  'IpProtocol=tcp,FromPort=53,ToPort=53,IpRanges=[{CidrIp=10.1.0.0/16}]' \
  'IpProtocol=udp,FromPort=53,ToPort=53,IpRanges=[{CidrIp=10.1.0.0/16}]' >/dev/null

# SG cho outbound endpoint: egress 53 TCP/UDP tới on-prem (SG mới mặc định cho phép mọi egress)
SG_OUT=$(aws ec2 create-security-group --group-name lab-r53-outbound --description "R53 outbound endpoint" --vpc-id $CLOUD --query GroupId --output text)

# SG cho DNS server 'on-prem': nhận 53 TCP/UDP từ VPC cloud (ENI của outbound endpoint)
SG_ON=$(aws ec2 create-security-group --group-name lab-onprem-dns --description "onprem dnsmasq" --vpc-id $ONPREM --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SG_ON --ip-permissions \
  'IpProtocol=tcp,FromPort=53,ToPort=53,IpRanges=[{CidrIp=10.0.0.0/16}]' \
  'IpProtocol=udp,FromPort=53,ToPort=53,IpRanges=[{CidrIp=10.0.0.0/16}]' >/dev/null

# SG cho EC2 client trong VPC cloud (không inbound)
SG_CL=$(aws ec2 create-security-group --group-name lab-cloud-client --description "client" --vpc-id $CLOUD --query GroupId --output text)
    Quy tắc SG cho endpoint: inbound endpoint cần ingress TCP+UDP 53 từ dải on-prem; outbound endpoint cần egress TCP+UDP 53 tới DNS server on-prem (SG mới tạo đã cho phép mọi egress; môi trường siết chặt phải mở rõ). Resolver dùng UDP là chính, TCP khi response lớn - phải mở cả hai.
  3. Lưu biến để dùng lại khi mất shell:
    for v in AWS_REGION CLOUD ONPREM SUB_A SUB_B SUB_ON RT_C RT_O IGW_C IGW_O PCX SG_IN SG_OUT SG_ON SG_CL; do echo "export $v=${!v}"; done > ~/lab-r53.env

2EC2: DNS server 'on-prem' (dnsmasq) và client

Cài dnsmasq trả lời app.corp.example → 10.1.1.50; client ở VPC cloud dùng để chạy dig.

  1. Tạo IAM role cho Session Manager:
    aws iam create-role --role-name lab-ssm-role --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}' >/dev/null
aws iam attach-role-policy --role-name lab-ssm-role --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore
aws iam create-instance-profile --instance-profile-name lab-ssm-profile >/dev/null
aws iam add-role-to-instance-profile --instance-profile-name lab-ssm-profile --role-name lab-ssm-role
sleep 15   # chờ IAM lan truyền
  2. Tạo file user-data cài dnsmasq (bind-interfaces để không đụng stub resolver 127.0.0.53 của systemd-resolved):
    cat > onprem-userdata.sh <<'EOF'
#!/bin/bash
dnf install -y dnsmasq bind-utils
cat > /etc/dnsmasq.d/corp.conf <<'CONF'
bind-interfaces
listen-address=127.0.0.1
listen-address=10.1.1.10
log-queries
log-facility=/var/log/dnsmasq.log
address=/app.corp.example/10.1.1.50
CONF
systemctl enable --now dnsmasq
EOF
  3. Chạy 2 instance:
    AMI=$(aws ssm get-parameter --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --query Parameter.Value --output text)

# DNS server 'on-prem' (IP cố định 10.1.1.10)
I_ON=$(aws ec2 run-instances --image-id $AMI --instance-type t3.micro --subnet-id $SUB_ON --private-ip-address 10.1.1.10 \
  --security-group-ids $SG_ON --associate-public-ip-address --iam-instance-profile Name=lab-ssm-profile \
  --user-data file://onprem-userdata.sh --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=lab-onprem-dns}]' \
  --query 'Instances[0].InstanceId' --output text)

# Client trong VPC cloud
I_CL=$(aws ec2 run-instances --image-id $AMI --instance-type t3.micro --subnet-id $SUB_A \
  --security-group-ids $SG_CL --associate-public-ip-address --iam-instance-profile Name=lab-ssm-profile \
  --user-data '#!/bin/bash
dnf install -y bind-utils' --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=lab-cloud-client}]' \
  --query 'Instances[0].InstanceId' --output text)
echo "export I_ON=$I_ON I_CL=$I_CL" >> ~/lab-r53.env
  4. Chờ ~2 phút rồi mở console EC2 → chọn instance → Connect → Session Manager (hoặc aws ssm start-session --target $I_CL nếu đã cài session-manager-plugin). Mở sẵn 2 tab: lab-cloud-client và lab-onprem-dns.
    Instance cần public IP + IGW chỉ để cài package và đăng ký Session Manager. DNS giữa hai VPC vẫn đi bằng IP private qua peering.
  5. Trên onprem-dns, kiểm tra dnsmasq đang trả lời:
    dig +short app.corp.example @10.1.1.10
    🔮 Dự đoán: Kết quả là gì? Và nếu hỏi web.aws.example (chưa tồn tại ở đâu cả) thì sao?
    Xem kết quảapp.corp.example → 10.1.1.50. web.aws.example → NXDOMAIN (hoặc không có answer): dnsmasq không biết zone này, hỏi lên DNS public cũng không có. Đây chính là vấn đề cần giải ở mục 5.

3Private Hosted Zone gắn với VPC cloud

Tạo PHZ aws.example gắn VPC cloud và test phân giải từ client trong chính VPC đó.

  1. Tạo PHZ + record web.aws.example:
    ZONE=$(aws route53 create-hosted-zone --name aws.example --caller-reference lab-phz-$(date +%s) \
  --vpc VPCRegion=ap-southeast-1,VPCId=$CLOUD \
  --hosted-zone-config Comment="lab PHZ",PrivateZone=true \
  --query HostedZone.Id --output text | sed 's#/hostedzone/##')
echo "export ZONE=$ZONE" >> ~/lab-r53.env

cat > rec.json <<'EOF'
{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{"Name":"web.aws.example","Type":"A","TTL":60,"ResourceRecords":[{"Value":"10.0.1.100"}]}}]}
EOF
aws route53 change-resource-record-sets --hosted-zone-id $ZONE --change-batch file://rec.json
    PHZ được tạo cùng một VPC liên kết ngay (--vpc). Muốn gắn thêm VPC cùng account: aws route53 associate-vpc-with-hosted-zone. VPC phải có enableDnsSupport và enableDnsHostnames = true.
  2. Trên cloud-client:
    dig +short web.aws.example
    🔮 Dự đoán: Client dùng DNS mặc định của VPC (VPC+2 = 10.0.0.2). Có phân giải được không, ra IP gì?
    Xem kết quảTrả về 10.0.1.100. Resolver của VPC thấy PHZ đã gắn với VPC nên trả lời nội bộ. (ví dụ output: 10.0.1.100)
  3. Trên cloud-client, thử tên on-prem:
    dig app.corp.example
    🔮 Dự đoán: Chưa có forwarding rule. Resolver trả gì?
    Xem kết quảstatus: NXDOMAIN — corp.example không tồn tại trên DNS public và chưa có rule forward. Ghi nhớ để so sánh sau mục 4.

4Outbound endpoint + forwarding rule (AWS → on-prem)

VPC cloud hỏi *.corp.example → Resolver chuyển tiếp qua outbound endpoint tới dnsmasq.

  1. Tạo outbound endpoint với 2 IP ở 2 subnet/2 AZ (tối thiểu 2 IP, nên khác AZ để chịu lỗi AZ):
    OUT=$(aws route53resolver create-resolver-endpoint --creator-request-id lab-out-$(date +%s) --name lab-outbound \
  --direction OUTBOUND --security-group-ids $SG_OUT \
  --ip-addresses SubnetId=$SUB_A SubnetId=$SUB_B \
  --query ResolverEndpoint.Id --output text)
echo "export OUT=$OUT" >> ~/lab-r53.env

# chờ OPERATIONAL (khoảng 3-6 phút)
until [ "$(aws route53resolver get-resolver-endpoint --resolver-endpoint-id $OUT --query ResolverEndpoint.Status --output text)" = OPERATIONAL ]; do echo -n .; sleep 15; done; echo OK
aws route53resolver list-resolver-endpoint-ip-addresses --resolver-endpoint-id $OUT --query 'IpAddresses[].[Ip,SubnetId,Status]' --output table
    🔮 Dự đoán: Bảng cuối liệt kê mấy IP, nằm trong dải nào, và status chuyển từ gì sang gì?
    Xem kết quả2 dòng, IP lấy tự động trong 10.0.1.0/24 và 10.0.2.0/24 (ví dụ 10.0.1.57, 10.0.2.141). Endpoint CREATING → OPERATIONAL; từ lúc này bắt đầu tính tiền theo ENI.
    Mỗi IP là một ENI trong subnet của bạn, tính khoảng $0.125/giờ. Đừng để qua đêm.
  2. Tạo rule FORWARD cho corp.example → 10.1.1.10:53 và associate với VPC:
    RULE=$(aws route53resolver create-resolver-rule --creator-request-id lab-rule-$(date +%s) --name fwd-corp-example \
  --rule-type FORWARD --domain-name corp.example --resolver-endpoint-id $OUT \
  --target-ips Ip=10.1.1.10,Port=53 --query ResolverRule.Id --output text)
echo "export RULE=$RULE" >> ~/lab-r53.env

ASSOC=$(aws route53resolver associate-resolver-rule --resolver-rule-id $RULE --vpc-id $CLOUD --name assoc-cloud \
  --query ResolverRuleAssociation.Id --output text)
echo "export ASSOC=$ASSOC" >> ~/lab-r53.env
aws route53resolver get-resolver-rule-association --resolver-rule-association-id $ASSOC --query ResolverRuleAssociation.Status --output text
    Rule không có tác dụng cho tới khi associate với VPC. Rule dạng FORWARD gắn một outbound endpoint; nhiều target IP được phép.
  3. Trên cloud-client:
    dig +short app.corp.example
    🔮 Dự đoán: Trước khi gắn rule là NXDOMAIN (mục 3). Bây giờ sao? Và dnsmasq log sẽ thấy query đến từ IP nào?
    Xem kết quảTrả 10.1.1.50. Trên onprem-dns chạy sudo tail -n 20 /var/log/dnsmasq.log: nguồn query là IP của các ENI outbound endpoint (dải 10.0.1.x/10.0.2.x), không phải IP của client. Hệ quả: firewall on-prem phải cho phép dải IP của endpoint, không phải cả dải workload.

5Inbound endpoint + conditional forwarder on-prem (on-prem → AWS)

Để on-prem phân giải PHZ: tạo inbound endpoint, rồi cấu hình DNS on-prem forward aws.example tới IP của endpoint.

  1. Tạo inbound endpoint (đặt IP cố định để dễ cấu hình on-prem):
    IN=$(aws route53resolver create-resolver-endpoint --creator-request-id lab-in-$(date +%s) --name lab-inbound \
  --direction INBOUND --security-group-ids $SG_IN \
  --ip-addresses SubnetId=$SUB_A,Ip=10.0.1.10 SubnetId=$SUB_B,Ip=10.0.2.10 \
  --query ResolverEndpoint.Id --output text)
echo "export IN=$IN" >> ~/lab-r53.env
until [ "$(aws route53resolver get-resolver-endpoint --resolver-endpoint-id $IN --query ResolverEndpoint.Status --output text)" = OPERATIONAL ]; do echo -n .; sleep 15; done; echo OK
aws route53resolver list-resolver-endpoint-ip-addresses --resolver-endpoint-id $IN --query 'IpAddresses[].Ip' --output text
    Xem kết quảIn ra 10.0.1.10 10.0.2.10 (ví dụ). Inbound endpoint nằm trong VPC cloud nên khi on-prem hỏi vào đây, Resolver trả lời theo ngữ cảnh VPC đó, thấy được PHZ đã gắn với VPC.
  2. Trên onprem-dns, trước khi thêm forwarder hãy thử lại:
    dig +short web.aws.example @10.1.1.10
    🔮 Dự đoán: Đã có inbound endpoint nhưng dnsmasq chưa biết gửi gì tới đó. Kết quả?
    Xem kết quảVẫn rỗng/NXDOMAIN. Inbound endpoint chỉ là 'cửa vào'; DNS on-prem phải được cấu hình conditional forwarder trỏ tới IP của endpoint.
  3. Thêm conditional forwarder và test lại:
    echo 'server=/aws.example/10.0.1.10/10.0.2.10' | sudo tee -a /etc/dnsmasq.d/corp.conf
sudo systemctl restart dnsmasq
dig +short web.aws.example @10.1.1.10
    🔮 Dự đoán: Lần này kết quả là gì? Server nào trong 2 IP được chọn?
    Xem kết quảTrả 10.0.1.100. dnsmasq dùng cả 2 IP (có thể xoay vòng/failover); mỗi IP ở một AZ khác nhau nên mất 1 AZ vẫn phân giải được. Trong thực tế (BIND/Windows DNS) bạn tạo conditional forwarder cho zone aws.example với cả 2 IP này.

6Mở rộng: RAM share rule, PHZ nhiều account, so với EC2 forwarder

Phần đọc/ghi nhớ — các lệnh dưới là mẫu (cần account thứ hai), không bắt buộc chạy.

6A. Chia sẻ forwarding rule qua AWS RAM

# Account sở hữu rule (network account)
aws ram create-resource-share --name share-fwd-rules \
  --resource-arns arn:aws:route53resolver:ap-southeast-1:<ACCOUNT_A>:resolver-rule/$RULE \
  --principals <ACCOUNT_B_ID hoặc ARN của Organization/OU>

# Account nhận (sau khi accept invitation, hoặc tự động nếu cùng Organization và bật sharing)
aws route53resolver associate-resolver-rule --resolver-rule-id <RULE_ID> --vpc-id <VPC_ACCOUNT_B>
Chỉ Resolver rule chia sẻ được qua RAM; endpoint thì không. Account nhận chỉ cần associate rule vào VPC của mình, query vẫn đi qua outbound endpoint của account chủ rule, nên VPC chứa endpoint phải route được tới on-prem. Mô hình chuẩn: 1 network account giữ endpoint + rules, share cho cả Organization.

6B. PHZ gắn VPC của account khác

# Account A (chủ zone): cho phép VPC của account B
aws route53 create-vpc-association-authorization --hosted-zone-id $ZONE \
  --vpc VPCRegion=ap-southeast-1,VPCId=<VPC_B>

# Account B (chủ VPC): thực hiện association
aws route53 associate-vpc-with-hosted-zone --hosted-zone-id <ZONE_ID> \
  --vpc VPCRegion=ap-southeast-1,VPCId=<VPC_B>

# Account A: xoá authorization sau khi xong (dọn dẹp)
aws route53 delete-vpc-association-authorization --hosted-zone-id $ZONE \
  --vpc VPCRegion=ap-southeast-1,VPCId=<VPC_B>
Không dùng được RAM cho hosted zone. Luồng bắt buộc: authorization (account chủ zone) → association (account chủ VPC). Bằng console không làm được bước authorization nên phải dùng CLI/API.

6C. So sánh các cách làm hybrid DNS

7💥 Phá thử

Cố ý làm hỏng từng thành phần để hiểu đúng điều kiện cần.

  1. Chặn port 53 ở DNS on-prem. Gỡ rule ingress của $SG_ON:
    aws ec2 revoke-security-group-ingress --group-id $SG_ON --ip-permissions \
  'IpProtocol=tcp,FromPort=53,ToPort=53,IpRanges=[{CidrIp=10.0.0.0/16}]' \
  'IpProtocol=udp,FromPort=53,ToPort=53,IpRanges=[{CidrIp=10.0.0.0/16}]'
    Trên cloud-client: time dig app.corp.example.
    🔮 Dự đoán: dig trả về status gì và mất bao lâu?
    Xem kết quảChậm vài giây rồi SERVFAIL (Resolver không tới được target; ví dụ ~ vài giây tới hơn 10 giây). Bài học: lỗi SG/NACL/route tới DNS on-prem hiện ra là SERVFAIL/timeout, không phải NXDOMAIN. Khôi phục bằng authorize-security-group-ingress với cùng tham số ở mục 1.
  2. Gỡ rule khỏi VPC.
    aws route53resolver disassociate-resolver-rule --resolver-rule-id $RULE --vpc-id $CLOUD
    Đợi ~30-60 giây, dig app.corp.example trên cloud-client.
    🔮 Dự đoán: Rule vẫn tồn tại, endpoint vẫn OPERATIONAL. Kết quả?
    Xem kết quảNXDOMAIN: rule chỉ có hiệu lực ở VPC đã associate. Gắn lại: aws route53resolver associate-resolver-rule --resolver-rule-id $RULE --vpc-id $CLOUD --name assoc-cloud (và cập nhật $ASSOC nếu cần dọn dẹp).
  3. Tắt enableDnsHostnames của VPC cloud:
    aws ec2 modify-vpc-attribute --vpc-id $CLOUD --no-enable-dns-hostnames
    Trên cloud-client: dig web.aws.example.
    🔮 Dự đoán: PHZ vẫn gắn với VPC. Còn phân giải được không?
    Xem kết quảKhông còn trả bản ghi PHZ (thường NXDOMAIN) — PHZ yêu cầu cả enableDnsSupport và enableDnsHostnames. Bật lại: aws ec2 modify-vpc-attribute --vpc-id $CLOUD --enable-dns-hostnames '{"Value":true}'. (Phản hồi có thể trễ vài chục giây; nếu thấy vẫn trả IP, đợi rồi thử lại.)

8🧹 Dọn dẹp

Thứ tự quan trọng: EC2 → rule association → rule → endpoint → PHZ → mạng → IAM.

# 0) nạp lại biến nếu mở shell mới:  source ~/lab-r53.env

# 1) Terminate EC2 và chờ
aws ec2 terminate-instances --instance-ids $I_ON $I_CL >/dev/null
aws ec2 wait instance-terminated --instance-ids $I_ON $I_CL

# 2) Gỡ rule khỏi VPC, chờ association biến mất, rồi xoá rule
aws route53resolver disassociate-resolver-rule --resolver-rule-id $RULE --vpc-id $CLOUD
until ! aws route53resolver get-resolver-rule-association --resolver-rule-association-id $ASSOC >/dev/null 2>&1; do sleep 10; done
aws route53resolver delete-resolver-rule --resolver-rule-id $RULE

# 3) Xoá 2 endpoint (outbound chỉ xoá được sau khi hết rule) -- chấm dứt tính tiền ENI
aws route53resolver delete-resolver-endpoint --resolver-endpoint-id $OUT
aws route53resolver delete-resolver-endpoint --resolver-endpoint-id $IN
until [ -z "$(aws route53resolver list-resolver-endpoints --query 'ResolverEndpoints[?Id==`'$OUT'` || Id==`'$IN'`].Id' --output text)" ]; do sleep 15; done

# 4) PHZ: xoá record rồi xoá zone
sed 's/UPSERT/DELETE/' rec.json > rec-del.json
aws route53 change-resource-record-sets --hosted-zone-id $ZONE --change-batch file://rec-del.json
aws route53 delete-hosted-zone --id $ZONE

# 5) Mạng: peering -> SG -> subnet -> IGW -> VPC
aws ec2 delete-vpc-peering-connection --vpc-peering-connection-id $PCX
for G in $SG_IN $SG_OUT $SG_ON $SG_CL; do aws ec2 delete-security-group --group-id $G; done
for S in $SUB_A $SUB_B $SUB_ON; do aws ec2 delete-subnet --subnet-id $S; done
aws ec2 detach-internet-gateway --internet-gateway-id $IGW_C --vpc-id $CLOUD;  aws ec2 delete-internet-gateway --internet-gateway-id $IGW_C
aws ec2 detach-internet-gateway --internet-gateway-id $IGW_O --vpc-id $ONPREM; aws ec2 delete-internet-gateway --internet-gateway-id $IGW_O
aws ec2 delete-vpc --vpc-id $CLOUD; aws ec2 delete-vpc --vpc-id $ONPREM

# 6) IAM
aws iam remove-role-from-instance-profile --instance-profile-name lab-ssm-profile --role-name lab-ssm-role
aws iam delete-instance-profile --instance-profile-name lab-ssm-profile
aws iam detach-role-policy --role-name lab-ssm-role --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore
aws iam delete-role --role-name lab-ssm-role
rm -f rec.json rec-del.json onprem-userdata.sh ~/lab-r53.env

# 7) Kiểm tra không còn endpoint nào
aws route53resolver list-resolver-endpoints --query 'ResolverEndpoints[].[Id,Name,Status]' --output table
Nếu delete-security-group báo DependencyViolation: ENI của endpoint chưa biến mất, đợi 1-2 phút rồi chạy lại. Nếu delete-resolver-endpoint bị từ chối: rule còn tham chiếu outbound endpoint - xoá rule trước. Sau cùng vào console Resolver, EC2, VPC kiểm tra lại không còn tài nguyên lab-*.

9🎯 3 câu hỏi kiểu đề

Tự đặt, không lấy từ bộ đề nào. Tự trả lời trước khi mở đáp án.

Câu 1

Một công ty nối data center với VPC bằng Direct Connect. Ứng dụng on-prem phải phân giải db.prod.aws.example (record trong Private Hosted Zone) và workload trong VPC phải phân giải *.corp.example do DNS on-prem quản lý. Yêu cầu: ít công việc vận hành nhất, chịu lỗi 1 AZ. Giải pháp nào phù hợp?

  1. Dựng cặp BIND server trên EC2 ở 2 AZ trong Auto Scaling group làm DNS forwarder hai chiều.
  2. Tạo inbound endpoint và outbound endpoint (mỗi cái ≥2 IP ở 2 AZ), forwarding rule cho corp.example tới DNS on-prem, và conditional forwarder trên DNS on-prem cho aws.example tới IP inbound endpoint.
  3. Tạo public hosted zone aws.example với cùng các record để on-prem phân giải qua Internet.
  4. Chỉ tạo outbound endpoint với rule cho aws.example trỏ về DNS on-prem.
Xem đáp án

Đáp án: B

Inbound = on-prem → AWS (phân giải PHZ), outbound = AWS → on-prem (forward corp.example). Managed, đa AZ. A hoạt động nhưng tốn vận hành. C lộ record nội bộ ra public. D đảo hướng: outbound không giúp on-prem hỏi AWS.

Câu 2

Tổ chức có 40 account trong AWS Organizations. Account 'network' đã có outbound endpoint và forwarding rule cho corp.example. Làm sao để VPC ở 39 account còn lại phân giải được corp.example mà không tạo thêm endpoint ở mỗi account?

  1. Chia sẻ outbound endpoint qua AWS RAM cho cả Organization.
  2. Chia sẻ Resolver rule qua AWS RAM; mỗi account associate rule với VPC của mình.
  3. Tạo VPC peering từ mọi VPC tới VPC của account network, DNS tự đi theo.
  4. Sao chép rule vào từng account và tạo outbound endpoint riêng cho từng account.
Xem đáp án

Đáp án: B

RAM chia sẻ được Resolver rule chứ không chia sẻ được endpoint. Account nhận associate rule vào VPC; query đi qua endpoint của account chủ rule. C không làm DNS forward theo peering. D đúng kỹ thuật nhưng tốn ENI/chi phí và không phải 'không tạo thêm endpoint'.

Câu 3

Account A sở hữu Private Hosted Zone internal.example (gắn với VPC của A). Một VPC ở account B (cùng region) cần phân giải zone này. Cả hai VPC đã bật enableDnsSupport và enableDnsHostnames. Bước nào đúng?

  1. Account B tạo PHZ cùng tên internal.example và sao chép toàn bộ record.
  2. Chia sẻ hosted zone qua AWS RAM cho account B.
  3. Account A chạy create-vpc-association-authorization cho VPC của B; sau đó account B chạy associate-vpc-with-hosted-zone.
  4. Tạo VPC peering giữa hai VPC; DNS tự phân giải PHZ qua peering.
Xem đáp án

Đáp án: C

PHZ khác account cần authorization từ chủ zone rồi association từ chủ VPC (làm bằng CLI/API). RAM không hỗ trợ hosted zone. Peering không mở rộng phạm vi PHZ. A tạo bản sao khó đồng bộ.

10📌 Quy tắc ghi nhớ

  • Inbound = on-prem hỏi vào AWS (PHZ); Outbound = AWS hỏi ra on-prem (forwarding rule).
  • Endpoint: ≥2 IP, 2 AZ, SG mở 53 TCP+UDP, tính tiền ~$0.125/ENI/giờ.
  • Rule phải associate với VPC mới có tác dụng; chia sẻ rule qua RAM, không chia sẻ endpoint.
  • PHZ cần enableDnsSupport + enableDnsHostnames; khác account: authorization → association (CLI).
  • Hybrid DNS trong đề: chọn Resolver endpoints, tránh EC2 forwarder tự quản trừ khi đề bắt buộc.
